# P05-30: P05-15 follow-up — Splitter / joiner components for bit-level access on placed chips

**Effort:** 6h (design + wiring) | **Gap:** GAP-3D-2 (bit-level access surfacing — completion)
**Phase section:** 0.5 follow-ups
**Depends:** P05-15 (landed 2026-05-24), [P05-12](./P05-12.md) (parent ticket — design + actions)

---

## Why this ticket exists

After P05-15 standardized chip placement on the builtin registry (2026-05-24
plan: [`docs/plans/2026-05-24-builtin-chip-placement-standardization.md`](../2026-05-24-builtin-chip-placement-standardization.md)),
the canvas can place all 16 Project 1 builtins — but each chip renders **one
socket per port**, with bus pins kept whole and labelled by width. That keeps
the visual surface uniform and the wiring rule simple, but it means **the only
way to wire a sub-bit or sub-bus signal into / out of a multi-bit chip is a
splitter or joiner**. The standardization plan explicitly deferred this:

> **Out-of-scope reminder:** Add bus splitter / joiner 3D components
> (P05-12) — bus pins remain whole; bit-level access is a future ticket.

This is that ticket — promoting [P05-12](./P05-12.md) from "Layer 1, TODO" to
"P05-15 follow-up, queued next." It also wraps in the two observed bugs that
will be unblocked or de-risked once splitter/joiner ships and multi-input
chips are spaced out:

- [B-003](../../development/observed-bugs.md#b-003--wiring-not-preserved-when-dragging-an-input-node-wired-to-a-multi-input-chip)
  — Drag-induced wire loss on 4-way mux.
- [B-004](../../development/observed-bugs.md#b-004--multi-input-chips-n--2-have-insufficient-pin-spacing-for-the-current-wiring-rule)
  — Multi-input chips (n > 2) lack pin spacing for valid wiring.

> **Implementation specifics live in [P05-12](./P05-12.md).** This ticket
> exists to (a) give the work a discoverable follow-up entry next to P05-29,
> (b) bind it to the post-P05-15 product context, and (c) cross-link the
> related observed bugs so they're triaged together.

## Goal

After this ticket:

1. Users can place a **splitter** (1 N-bit input → N 1-bit outputs) on the canvas.
2. Users can place a **joiner** (N 1-bit inputs → 1 N-bit output) on the canvas.
3. Both components route via the existing wiring rule and can be wired to any
   builtin chip's bus pin, enabling bit-level access to Mux/DMux/Or/And/Not 16
   and the 4-/8-way variants without per-pin breakouts on the chip body.
4. Persistence round-trips a circuit containing splitter/joiner.
5. The two observed bugs above (B-003, B-004) are either resolved as a
   side-effect, demoted to follow-ups, or re-triaged with new repro evidence
   after the layout work.

## Out of scope (defer)

- **Bit-level pin breakouts on the chip body itself** — would require a
  redesigned `ChipBody3D` with N sockets per N-bit port. Deferred per the
  2026-05-24 standardization plan; splitter/joiner is the chosen access path.
- **Thick-wire visual treatment for `width > 1` buses** — covered in P05-12;
  ship if it falls naturally out of the splitter/joiner work, otherwise track
  as a P05-29-style polish follow-up.
- **HDL-side splitter/joiner equivalents** — coordinate with P05-16 / P05-26.

## Verifiability

| Layer | Requirement |
|-------|----------------|
| **Vitest** | Inherit P05-12's `placeBusSplitter` / `placeBusJoiner` store tests; add a round-trip persistence case asserting a splitter+joiner circuit serializes and re-loads with all wires intact. |
| **Store E2E** | New `@store` spec under `e2e/specs/builtins/` that places `Mux4Way16` + an `InputNode` + a splitter, wires all 4 select-or-data ports through the splitter, runs the simulation, and asserts the output. Same test should fail today (B-004) and pass post-fix. |
| **Manual UI** | Light + dark theme: place each multi-bit Project 1 chip → splitter → InputNodes for each bit → confirm wiring follows drag (B-003 regression check). |
