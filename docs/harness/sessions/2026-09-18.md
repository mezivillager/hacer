# Session record — 2026-09-18: repositioning HACER for autonomous agent development

The committed memory of one long working session, written so the work can resume from the repo alone
if the conversation is lost. What to do *next* is never kept here — it lives in `docs/portfolio.md`
and GitHub Issues. This page records the goal, what was decided and built, the state at close, and
how to pick up.

## 1. The goal

The owner's brief, condensed: HACER was meant to be built by autonomous AI agents with little human
oversight, but a 3D renderer that is hard to QA, a weak laptop, bulky PRs and no queue got in the
way. Research best practice and **reposition the repo so agents (mainly Claude) can steer it
forward with very little oversight** — easier-to-test surfaces (2D, HDL, MCP/API) growing in
parallel with 3D, cloud execution for heavy work, an independent AI QA, small PRs, a prioritised
queue, and a workflow agents follow and keep improving. End state: "Claude, list the priority
projects", "what's open in X", "what can you pick up", "work the next items", "queue up more".

The research that answered it: `docs/research/2026-09-18-agent-readiness/` (`REPORT.md`,
`WORK-SYSTEM.md`, `DECISIONS.md` — every judgment call R1–R84 with its cost if wrong and revert).

## 2. The owner's rulings during the session (verbatim, in order)

1. Permissions: "all necessary permissions are granted, no restriction on github pushing, deploying, releasing, etc … this is personal project"; "nothing is private, it's an open project".
2. "what I want to do next is ask claude what can you do next to get things moving forward? and then it picks it up and works on it creates a pr and merges" — and "the entire process we are setting up should be reviewable and adjustable as well, and maintaining and improving that entire process as well needs its own queue".

4. Browser testing: "we need browser testing to be done in cloud for 3d, but 2d and other browser testing can be done locally also"; "all critical features/fixes has to pass throw an independent qa that does browser testing" (→ ADR-0016 #220, QA agent #257).
5. Priority: "priority is for other surfaces (2d, hdl and mcp) to catch up with 3d, and note the non-3d surfaces have to grow hand in hand"; "that will means there's a whole lot of core refactoring … lots of architectural decision and designing"; "I meant that feature wise, of course the process ironing, and other auxiliary items are also of equal priority" (→ #259).
6. Docs: "a public documentation layer (for all possible consumers of the platform, api consumers, mcp consumers, etc) that grows in parallel"; "research the state of the art best practice documentation approaches and do everything needed to take that live, deployment, etc" (→ epic #260, ADR-0017).
7. Engineering truth: "a product agent that mimics product and R&D team, continually researching the engineering/logic/science aspect … so we are not building something fake and everything … is under constraint of physics, digital logic, etc"; "when product agents wants to create tasks/issues/etc, it should get my approval however, but until then, it should keep queing up items"; "name it better … we might need a real product agent that also monitors the usability and design part" (→ fidelity role #268, ADR-0018; product role #269).
8. The team: "we need a team of agents/project-scoped to collaborate productively and efficiently"; "research best practices around the idea and refine my suggestions, and make sure process is in place to refine the entire setup continually, learning from practice" (→ #270, #271).
9. Close: "wrap up current on-going prs and tasks, and call it a day"; "make sure there's committed context … so nothing is lost".

## 5. How to resume

1. Read `docs/harness/README.md` (the loop and where every knob lives) and `docs/portfolio.md`.
2. `node scripts/backlog.mjs projects` and `node scripts/backlog.mjs ready`.
3. Say **"what can you do next?"** — the `ha-next` skill presents the top pick; "work it" takes it
   through claim → build (`docs/harness/implementer-brief.md`) → PR → verifier
   (`docs/harness/verifier-brief.md`) → merge → ledger.
4. Check the four in-flight items above first: `gh pr list --state open` and the `claim/*` refs
   (`git ls-remote --heads origin 'claim/*'`) — a claim with no open PR is stale; release it.

## 6. What the session learned

`docs/harness/ledger.md` holds every failure and what it became. The ones worth remembering:
a fresh-context verifier caught defects the builders' tests missed three times in eight PRs; a new
required check must be tried on bot PRs before it is required; removing the ruleset bypass broke
releases until ADR-0015; steering changes must go into the **issue body**, not only into messages,
because the issue is what an agent re-reads.
