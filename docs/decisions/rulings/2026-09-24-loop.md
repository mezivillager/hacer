## R518 — my own R517 fix shipped a safety hole; the tool's first live run caught it
Builds on: R517
Amends: R517
R517's fix printed its required set on the very next run:
`required on main: {"message":"Branch not protected",…},browser-qa,ci,pr-hygiene`.
`gh` writes API **error bodies to stdout**, so the unprotected-branch 404 was being read as a
context name. That is not cosmetic. The script decides "do I know the required set?" by testing
whether the file is non-empty — so in a repo with **no** rulesets, the file would contain nothing
but that 404 line, the script would believe it knew the requirements, and **every real failure
would be classified non-blocking**. The fix I wrote to stop the tool refusing good merges could
have made it accept bad ones.

Fixed: a `clean()` filter drops JSON-ish lines, and classic protection is consulted **only** when
the rulesets yield nothing (correct precedence rather than a blind union).
Verified, not asserted — both paths return exactly `ci,pr-hygiene,browser-qa`, and `clean()` fed the
real 404 body plus `ci` emits only `ci`.
**Cost if wrong:** unchanged from R517 — bounded by the repo's own stated gate.
**Lesson, and it is the #394 class again:** I wrote R517 as a finished fix and said so before its
first run. The run disproved part of it within two minutes. The evidence existed *because the fix
printed what it had concluded* — the diagnostic line is what caught it, not review. Make the tool
state its premise out loud; that is what makes a wrong premise visible.
