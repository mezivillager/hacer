## Context

After P05-02, store values are `number` bitmasks and input/output nodes carry a `width`. After P05-10, `PinoutPanel` can display multi-bit node widths but deliberately leaves multi-bit editing to P05-13.

The remaining bus-simulation gap is not value storage; it is width-aware propagation. `Wire` has no width metadata, store `Pin` has no width metadata, `topologicalEval` copies raw numbers without clamping, and the UI/store currently reject direct input-node to output-node wiring.

P05-11 should make direct input-node to output-node pass-through wiring legal for matching-width endpoints. That gives HACER a simple, no-gate way to represent pass-through chip behavior and provides the cleanest acceptance test for multi-bit wire propagation. If the implementer decides to reject direct pass-through instead, they must remove the direct input-to-output acceptance criteria and replace them with the first legal bus-aware component available in the same implementation.

nand2tetris web-ide represents a bus as bit storage plus a numeric `busVoltage` bitmask. `InSubBus` and `OutSubBus` in `simulator/src/chip/chip.ts` implement range reads and writes with the same masking model as `readSubBus` and `writeSubBus`. HACER should store values as bitmasks and keep sub-bus helpers pure until the HDL compiler maps ranges to concrete wires.

## Goal

After this ticket:

1. `readSubBus(value, startBit, numBits)` extracts bits from a bitmask.
2. `writeSubBus(target, value, startBit, numBits)` writes bits into a bitmask.
3. `clampToWidth(value, width)` is the shared helper for propagation, gate inputs, output-node writes, and future UI formatters.
4. Store `Pin` and `Wire` types can represent width metadata without breaking existing single-bit circuits.
5. New wires infer `width` from endpoint widths, with legacy missing `wire.width` treated as `1`.
6. `topologicalEval` clamps propagated values to wire and destination widths.
7. Direct input-node to output-node pass-through wiring is supported for matching-width endpoints, so a no-gate bus pass-through circuit is representable.
8. A 16-bit input wired to a 16-bit output propagates the full value in a single eval.

## Files to Create

### `src/simulation/busOps.ts`

```typescript
/**
 * Create a bitmask with `numBits` ones starting at bit 0.
 * maskForWidth(8) => 0xFF, maskForWidth(16) => 0xFFFF
 */
export function maskForWidth(numBits: number): number {
  if (numBits <= 0) return 0
  if (numBits >= 32) return 0xFFFFFFFF >>> 0
  return ((1 << numBits) - 1) >>> 0
}

/**
 * Read `numBits` bits starting at `startBit` from `value`.
 * readSubBus(0xFF00, 8, 8) => 0xFF
 */
export function readSubBus(value: number, startBit: number, numBits: number): number {
  return ((value >>> startBit) & maskForWidth(numBits)) >>> 0
}

/**
 * Write `numBits` bits of `subValue` into `target` starting at `startBit`.
 * writeSubBus(0, 0xFF, 8, 8) => 0xFF00
 */
export function writeSubBus(target: number, subValue: number, startBit: number, numBits: number): number {
  const mask = maskForWidth(numBits) << startBit
  return ((target & ~mask) | ((subValue << startBit) & mask)) >>> 0
}

/**
 * Clamp a value to the given bit width.
 * clampToWidth(0x1FFFF, 16) => 0xFFFF
 */
export function clampToWidth(value: number, width: number): number {
  return (value & maskForWidth(width)) >>> 0
}
```

### `src/simulation/busOps.test.ts`

```typescript
import { describe, it, expect } from 'vitest'
import { maskForWidth, readSubBus, writeSubBus, clampToWidth } from './busOps'

describe('maskForWidth', () => {
  it('returns 0 for non-positive widths', () => {
    expect(maskForWidth(0)).toBe(0)
    expect(maskForWidth(-1)).toBe(0)
  })

  it('returns masks for Project 1 widths', () => {
    expect(maskForWidth(1)).toBe(0x1)
    expect(maskForWidth(8)).toBe(0xFF)
    expect(maskForWidth(16)).toBe(0xFFFF)
  })

  it('caps widths of 32 or more at an unsigned 32-bit mask', () => {
    expect(maskForWidth(32)).toBe(0xFFFFFFFF >>> 0)
    expect(maskForWidth(64)).toBe(0xFFFFFFFF >>> 0)
  })
})

describe('readSubBus', () => {
  it('reads lower and upper bytes', () => {
    expect(readSubBus(0xFF00, 0, 8)).toBe(0)
    expect(readSubBus(0xFF00, 8, 8)).toBe(0xFF)
  })

  it('reads single bits and full 16-bit values', () => {
    expect(readSubBus(0b1010, 1, 1)).toBe(1)
    expect(readSubBus(0b1010, 0, 1)).toBe(0)
    expect(readSubBus(0x1234, 0, 16)).toBe(0x1234)
  })
})

describe('writeSubBus', () => {
  it('writes byte ranges while preserving unrelated bits', () => {
    expect(writeSubBus(0, 0xFF, 8, 8)).toBe(0xFF00)
    expect(writeSubBus(0xFF00, 0xAB, 0, 8)).toBe(0xFFAB)
  })

  it('round-trips with readSubBus', () => {
    const value = writeSubBus(0, 0x42, 4, 8)
    expect(readSubBus(value, 4, 8)).toBe(0x42)
  })
})

describe('clampToWidth', () => {
  it('clamps oversized values to the requested width', () => {
    expect(clampToWidth(0x1FFFF, 16)).toBe(0xFFFF)
  })

  it('leaves values unchanged when they fit', () => {
    expect(clampToWidth(0xFF, 16)).toBe(0xFF)
  })
})
```

### Type updates (`src/store/types.ts`)

```typescript
export interface Pin {
  id: string
  name: string
  type: 'input' | 'output'
  value: number
  width?: number // default 1 for existing primitive gate pins
}

export interface Wire {
  id: string
  signalId?: string
  from: WireEndpoint
  to: WireEndpoint
  segments: WireSegment[]
  crossesWireIds: string[]
  width?: number // default 1; inferred from endpoint widths at creation when omitted
}
```

### Endpoint width rules

- `InputNode.width` and `OutputNode.width` are authoritative for node endpoints.
- `Pin.width ?? 1` is authoritative for gate endpoints.
- `Wire.width` should be inferred as `Math.min(sourceWidth, destinationWidth)` unless a future HDL/sub-bus compiler provides a narrower explicit width.
- Existing wires without `width` behave as `width: 1` for backward compatibility.
- A 16-bit source feeding a 1-bit primitive gate input clamps to the least significant bit through `clampToWidth(value, 1)`.

### Bus operation edge cases

- Widths less than or equal to 0 produce mask `0`.
- Widths from 1 through 31 use `(1 << width) - 1` with unsigned coercion.
- Widths 32 and above produce `0xFFFFFFFF >>> 0`; HACER Project 1 only requires up to 16 bits.
- `clampToWidth(value, width)` is the shared helper for propagation, gate inputs, output-node writes, and future UI formatters.

## Pitfalls

- **Backward compatibility:** All existing wires have no `width` field. Treat `undefined` as `width: 1`; existing tests must not break.
- **Endpoint width inference:** A `Wire.width` invariant is not meaningful unless gate pins have `width` or the code consistently uses `Pin.width ?? 1`.
- **Direct pass-through:** The current store rejects input-node to output-node wires in `addWire`, and UI wiring rejects that flow in `completeWiringToNode`. Update both paths if direct pass-through remains in scope.
- **Primitive gate width:** Existing primitive gates are still one-bit components. Clamp wide input values before assigning gate input pins instead of silently storing wide values in scalar pins.
- **JavaScript bitwise ops:** `|`, `&`, `^`, `~`, `<<`, and `>>` operate on 32-bit signed integers. Use `>>> 0` to coerce to unsigned where needed. Values above 32 bits are not needed for Project 1.
- **Sub-bus ranges:** Keep sub-bus helpers pure in P05-11. P05-16 can later map HDL ranges to explicit wire/sub-bus metadata.
- **P05-12 and P05-13:** Keep `maskForWidth`, `readSubBus`, `writeSubBus`, and `clampToWidth` stable so bus 3D components and multi-bit UI can reuse them.
- **Immer drafts:** When modifying `state.outputNodes[i].value = newValue` inside `set()`, Immer handles the mutation. Don't spread.
