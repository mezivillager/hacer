# R1 rendering-research review

**Verdict: sound with corrections.** The overwhelming majority of ~90 checked claims (repo greps, `npm view`, primary-source `curl`) are precise, often to the exact byte/commit/timestamp. But there are real errors: a repeated arithmetic mistake (sphere triangle count, tagged **[E]** three times), a version claim that's wrong for HACER's own locked dependency, a wrong file/line citation that undersells the repo's actual test architecture, an issue-vs-PR conflation, and one competitor quote that omits a materially-qualifying sentence from the same source paragraph. None of these flip the core recommendations (stay on three+R3F, instance pins with a picking map, defer WebGPU, keep DOM labels) — they're corrections, not reversals. The note's own late self-corrections (gl, @react-three/a11y dates) are verified accurate.

## Reasoning attacks

- **"Stay on three + R3F" is well-supported, not thin.** Precise, dated, independently-reproducible numbers throughout (downloads, commit counts, issue states) — better sourced than most vendor-comparison writeups. The Babylon trade-off (0.06%-adoption binding to buy a headless engine) is quantitatively sound and I confirmed the two download figures independently.
- **Drei-coupling risk is accurately stated, if anything slightly under-sold.** 4 commits/6mo by one author and 54 open PRs both check out exactly. The note could have made the risk *stronger* by correctly noting the triage issue's own count (51) vs. today's (54) as evidence of an accelerating backlog, instead of miscasting that issue as one of the PRs.
- **No conflict found with read-only / pure-layout / headless-CI.** `frameloop="demand"` unconditionally actually fits *better* under read-only (far fewer mutation paths need `invalidate()` than the note implies for a general app). The CI-benchmark recommendation correctly stays inside `@react-three/test-renderer` + `renderer.info`, never a real GPU. `layout`/`route` are never touched by any rendering recommendation.
- **Instancing-breaks-picking claim and the instanceId→node-id map are sound.** `InstancedMesh.raycast()` genuinely loops the full instance count (confirmed in source); for a viewer whose only interaction *is* hover/click-to-inspect (per REPORT §4), this is correctly treated as a real cost needing a real fix, and pairing it with `three-mesh-bvh` (also confirmed current/maintained) is the standard mitigation. Sound.
- **"Defer WebGPU" is evidence-driven, not merely cautious**, and holds up even better after independent checks: the caniuse table is exact across all 6 browser rows, and the bundle-size penalty is now independently re-measured (2.281× gzip), not just cited. The deck.gl misquote (#57) is the one place "WebGPU is further along elsewhere" leans on a source that actually undercuts itself — deck.gl's own release notes call their WebGPU support experimental and not production-ready, the same maturity tier as three.js's, which somewhat weakens the "bellwether ahead of three.js" framing in the watch list.
- **§4's triangle/mesh table is presented as computed and is flagged as such in "Could not verify"** — good practice — but individual numbers pulled from it are re-tagged **[E]** in the Recommendations section (e.g. rec 3ii: "512 triangles each **[E]**") without the hedge, which compounds the arithmetic error (#13) by presenting a wrong, unreconciled number with an evidence tag.
- **No instance found of the note talking down the 3D view.** §7's "the owner's differentiator claim is literally true within this field," the explicit defense of DOM labels ("right and should be defended, not reversed"), and the tscircuit find framed as validating (not competing with) HACER's direction are all consistent with the constraint.

## What's missing for a decision-maker

- No sizing of the "vendor drei's four components" fallback (`Text`, `Html`, `Instances`, controls) if drei stalls further — named as the trigger response, not scoped.
- No DOM-node-count threshold behind "2,000 labels is a DOM problem" — asserted, not bounded, so "cull by zoom level" has no target to design against.
- No reconciliation between §4's mesh/triangle budget and §5's wire cost into one total-scene-cost figure — a reader cannot get HACER's actual worst-case draw-call count from this note.
- No interaction between the proposed `instanceId`→node-id picking map and the hierarchy-level LOD model (§4) — what happens to picking when a composite chip collapses/expands is unaddressed.
- Given the read-only decision, no mention of prerendering/static scene export as an alternative lever (only runtime rendering techniques are considered).
