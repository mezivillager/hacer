# F2 — Outside research: structuring a codebase for autonomous agent development

Scope: external knowledge only; I did not audit HACER's code (F1 is doing that). All URLs fetched **2026-09-21** unless another date is given. Tags: **[E]** = measured study, primary documentation, or registry/source data I read directly. **[O]** = practitioner essay, vendor post, community consensus. **[E-snip]** = search-engine summary I could not open — a lead, not a citation.

## Q1 — What repository properties predict agent success or failure?

**Change size and file-spread dominate. [E]** *SWE-bench Goes Live!* (Zhang et al., Microsoft; 1,319 instances, 93 Python repos), https://arxiv.org/html/2505.23419v2 : "a single-file patch that changes fewer than five lines is solved almost one time in two (48%)"; "once the patch edits three or more files, or spans more than one hundred lines, the success rate falls below ten per-cent"; "patches that touch seven or more files are never solved." Same paper: repos under 100 files "often exceed 20% success rates, while those exceeding 500 files rarely reach 5%" — correlational (big repos host harder issues); the patch-shape number is the sturdier one.

**Localisation is largely solved; coherent editing is not. [E]** *Coherence Collapse* (Kim et al., 16,758 trajectories, SWE-bench Verified + PolyBench), https://arxiv.org/abs/2603.24631 : "60-69% of failures on SWE-Agent and OpenHands reach and edit the correct functions yet still produce incorrect patches"; in 5 cases the agent produced a patch bit-identical to the gold reference mid-trajectory "and destroys it later," all 5 recovered by an edit-commit checkpoint. Corroborated **[E]** https://arxiv.org/abs/2511.00197 : "most trajectories correctly identify problematic files (72-81% even in failures)" and "failed trajectories are consistently longer and exhibit higher variance than successful ones." → The lever is not better search; it is smaller blast radius and checkpointed, verifiable steps.

**Tests passing ≠ acceptable. [E]** METR, https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/ (2026-03-10): 4 maintainers from 3 SWE-bench Verified repos reviewed 296 AI PRs; the automated grader scored "on average about 24.2 percentage points (standard error: 2.7) higher than the maintainer merge decision"; roughly half of test-passing PRs would not be merged; golden patches merged only 68% of the time. Rejection reasons: core functionality failure, "breaks other code," code quality / repo standards. Authors' caveat: agents got one attempt and no review iteration.

**Agent PRs fail the same way in the wild. [E]** *Where Do AI Coding Agents Fail?* (Ehsani et al., MSR 2026; 33k agent-authored PRs, 5 agents), https://arxiv.org/abs/2601.15195 : "not-merged PRs tend to involve larger code changes, touch more files, and often do not pass the project's CI/CD pipeline validation"; docs/CI/build tasks merge best, "performance and bug-fix tasks perform the worst."

**Most failure is specification and context, not damage. [E]** 20,574 real sessions, 1,639 repos, https://arxiv.org/abs/2605.29442 : 90.50% of pushback episodes impose effort/trust cost rather than irreversible damage; 91.49% of resolutions required explicit user correction; failure forms include "project reading," rule adherence and action-bounding; constraint violations and inaccurate self-reporting rise proportionally over time.

**Context length degrades accuracy before the window is full. [E]** Chroma, 18 frontier models, difficulty held constant (2025-07-14), https://www.trychroma.com/research/context-rot : every model degrades with input length; one distractor hurts, four hurt more; LongMemEval shows a large gap between ~300-token focused input and ~113k full input. "Whether relevant information is present in a model's context is not all that matters; what matters more is how that information is presented." Anthropic's framing **[E]** (2025-09-29) https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents : "context must be treated as a finite resource with diminishing marginal returns"; prefer just-in-time retrieval; avoid "bloated tool sets"; "if a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better."

**Agents navigate by surface structure and lose a lot when it is perturbed. [E]** RepoMirage, https://arxiv.org/abs/2605.26177 : under three semantics-preserving repository-level perturbations average performance fell **66.8% → 25.3%**, with "exploration drift, where agents access broader repository context but fail to turn it into effective structure information." → Legible, conventional structure is load-bearing, not cosmetic.

**Code health correlates with cost — for humans. [E]** *Code Red* (Tornhill & Borg, TechDebt 2022; 39 proprietary codebases, 30,737 files), https://arxiv.org/abs/2203.04374 : low-quality code "contains 15 times more defects," issues take "124% more time in development," with "9 times longer maximum cycle times." Transfer to agents is inference, not evidence.

**The one direct code-health→agent measurement is vendor-run. [O]** CodeScene (2026-06-25), https://codescene.com/blog/code-health-a-prerequisite-for-successful-agent-deployment : with CodeHealth guidance Claude removed all smells in 52% of files (vs 5.7% without) and reached a healthy state in 90%+ (vs 24.1%), test pass rate ~95%; also cites newcomers needing 45% more time on unhealthy code for small changes, 93% for larger. Directionally interesting; it is the vendor measuring its own metric.

**Human-productivity results are mixed; repo maturity is the moderator.** METR RCT **[E]** https://arxiv.org/abs/2507.09089 : 16 experienced OSS devs, 246 tasks, ~5 years mean repo familiarity — allowing AI *increased* completion time by 19%. Counterweight **[E]** *Echoes of AI* (Borg et al., 151 participants, two-phase controlled experiment) https://arxiv.org/abs/2507.00788 : 30.7% median completion-time reduction with AI in phase 1, and "no significant differences in subsequent evolution with respect to completion time or code quality" in phase 2. Neither supports a general law; the setting decides.

**Folklore watch.** Repeated everywhere but *not* evidenced in anything I fetched: file-length thresholds ("keep files under 300 lines"), cyclomatic-complexity thresholds for agent success, and "splitting into packages makes agents better." Files-touched and change size are evidenced; per-file length is not. The usual PR-size citation (SmartBear/Cisco, 2,500 reviews / 3.2M lines, detection peaking under 200-400 lines) is **[E-snip]** only: https://static1.smartbear.co/support/media/resources/cc/book/code-review-cisco-case-study.pdf

**dependency-cruiser is the best fit and the only one with a native shrink-only ratchet. [E]** https://github.com/sverweij/dependency-cruiser/blob/main/doc/cli.md : `depcruise src --baseline` writes `.dependency-cruiser-known-violations.json`; `--ignore-known` lowers known violations to `ignore` and prints "X known violations ignored"; `--baseline-mode` takes `full`, **`shrink-only`** (removes violations only, never adds) and `format`; the `err` reporter exits with a code equal to the violation count, i.e. a CI gate. Cost in a single-package Vite app: one config file plus one CI step, no build-system change.

**ESLint bulk suppressions are the generic ratchet, and they ratchet by default. [E]** https://eslint.org/docs/latest/use/suppressions : `--suppress-all` writes `eslint-suppressions.json` (commit it); when a suppressed violation is later fixed "ESLint will exit with a non-zero exit code and an error is reported about unused suppressions" unless `--pass-on-unpruned-suppressions` is passed; `--prune-suppressions` cleans up; only `"error"`-level rules are suppressed. Introduced in ESLint v9.24.0, April 2025 (**[E-snip]** https://eslint.org/blog/2025/04/introducing-bulk-suppressions/). → boundaries/import-x rules become adoptable on day one with no big-bang cleanup.

**Betterer, tsarch and madge are effectively stale [E]** — no release in 21–25 months, Betterer's newest artefact an alpha. Don't build a ratchet on them when dependency-cruiser and ESLint shipped this month.

**TypeScript project references enforce a real boundary at real cost. [E]** https://www.typescriptlang.org/docs/handbook/project-references.html : referenced projects need `composite: true` and declaration emit; "importing modules from a referenced project will instead load its *output* declaration file (`.d.ts`)" — that is what makes the boundary unbypassable; `tsc -b` "effectively acts as if `noEmitOnError` is enabled for all projects"; and you must "either check in certain build outputs *or* build a project after cloning it before you can navigate the project in an editor without seeing spurious errors." Materially changed: **TypeScript 7.0.2 is published (2026-07-08, Apache-2.0)** — the native Go compiler, reported at 8–12x faster full builds (**[E]** registry; **[E-snip]** https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/). A multi-project `tsc -b` graph is far cheaper than it was.

**Nx boundary rules [E]** https://nx.dev/features/enforce-module-boundaries : tags per project (`"tags": ["scope:client"]`), enforced via `depConstraints` / `onlyDependOnLibsWithTags`; the docs distinguish the import-level ESLint rule from the graph-level Conformance plugin. Whether the ESLint rule works with *no* Nx project configuration I could **not** confirm — it reads project tags, which implies Nx project files.

**"Modular monolith" concretely:** one build/deploy unit, internally decomposed into modules with explicit public APIs whose boundaries are "explicit and enforced… backed by tooling and testing" — **[O]**, search-summary consensus, no canonical primary definition found. The best concrete artefact is Shopify's **Packwerk [E]** https://github.com/Shopify/packwerk : enforces package boundaries and constant visibility by static analysis, actively maintained, and designed to "avoid false positives… at any cost," accepting false negatives instead. That trade-off is worth copying for any gate an agent has to live with.

**When to split into pnpm workspace packages (solo dev + agents):** no study found. Defensible rule from the above: split when you need a boundary the tooling *cannot* be talked out of (project references, separate package deps) — lint-level boundaries buy most of the enforcement for near-zero cost; package boundaries buy the rest plus independent consumability, at the price of Vite aliasing, tsconfig graph, test config and build ordering. **[O]**

## Q3 — Architecture fitness functions

**Definition (primary) [E]** Thoughtworks Technology Radar, ring **Trial**, Nov 2017 (updated May 2018), https://www.thoughtworks.com/radar/techniques/architectural-fitness-function : "A fitness function is used to summarize how close a given design solution is to achieving the set aims… provides an objective integrity assessment of some architectural characteristics, which may encompass existing verification criteria, such as unit testing, metrics, monitors."

**Concrete JS/TS fitness functions, all CI-runnable today [E]:** cycles + layer rules via `depcruise --validate` (exit code = violation count); dead code via `knip`; public API surface via API Extractor's checked-in `.api.md` (a diff is a visible contract change) and `publint` 0.3.24 for manifest correctness; bundle/perf budget via size-limit — "checks every commit on CI, calculates the real cost of your JS for end-users and throws an error if the cost exceeds the limit," and it budgets *time* (`"limit": "500 ms"`) as well as bytes, with a PR-commenting GitHub Action (https://raw.githubusercontent.com/ai/size-limit/main/README.md); architecture assertions as tests via tsarch — but stale.

**Keeping them from becoming noise.** (1) Packwerk's rule: prefer false negatives over false positives **[E]**. (2) Anthropic on adversarial reviewers **[E]** https://code.claude.com/docs/en/best-practices : "A reviewer prompted to find gaps will usually report some, even when the work is sound, because that is what it was asked to do. Chasing every finding leads to over-engineering… Tell the reviewer to flag only gaps that affect correctness or the stated requirements." (3) Böckeler **[O]** (2026-04-02) https://martinfowler.com/articles/harness-engineering.html : distribute checks by cost — cheap ones pre-integration, expensive ones (mutation testing, deep review) post-integration, because "the earlier you find issues, the cheaper they are to fix" — and notes "clearly definable module boundaries afford architectural constraint rules."

## Q4 — The shape this kind of product wants

**Hexagonal architecture's stated intent is literally agent parity. [E]** Cockburn (2005-09-04, v0.9), https://alistair.cockburn.us/hexagonal-architecture/ : the pattern exists to "allow an application to equally be driven by users, programs, automated test or batch scripts," and the pay-off he names is that "the test or QA department can run automated test scripts against the application" when "every piece of functionality the application offers were available through an API," including headless operation "where applications function purely through their API." → "AI-agent parity" is the 2005 ports-and-adapters requirement with a new client.

**nand2tetris web-ide — verified by local source read. [E]** (the `web-ide` checkout beside this repo, 2026-09-21): an npm-workspaces monorepo of 8 packages (`cli`, `components`, `extension`, `extension/views/hdl`, `projects`, `runner`, `simulator`, `web`). `simulator/package.json` depends only on `@davidsouther/jiffies`, `@nand2tetris/projects`, `@nand2tetris/runner`, `ohm-js`, `rxjs`, `@types/node` — **no React, no DOM**; `command grep -rl "from 'react'" simulator/src` returns 0 of 83 `.ts` files. The React app (`web`) consumes `simulator`, `components` and `projects` by `file:` links; `cli` is a separate consumer of the same core. → HACER's own reference implementation already proves core + multiple surfaces with plain workspace packages and no framework in the core.

**tldraw. [E]** `@tldraw/editor` 5.4.2 and `@tldraw/store` 5.4.2 (2026-09-10; store MIT, editor ships its own licence — check before copying code). https://tldraw.dev/docs/editor : "The `Editor` class is the main way of controlling tldraw's editor… Almost everything is available through it," reachable via `onMount` or `useEditor`; the store is "the reactive database holding all records." https://tldraw.dev/docs/persistence : "The snapshot has two parts: `document` (shapes, pages, bindings) which you typically save to a server, and `session` (camera, selection, UI state) which you keep per-user locally." History is transactional — `Editor.run` batches into "a single undo step" and accepts `history: 'ignore' | 'record-preserveRedoStack'`. → Three transferable ideas: one façade that *is* the programmatic API; document vs session split at the snapshot level; explicit history mode on every mutation entry point.

**xyflow. [E]** `@xyflow/system` 0.0.82 (2026-09-01, MIT), https://raw.githubusercontent.com/xyflow/xyflow/main/packages/system/README.md : "provides core, framework-agnostic helpers and types for building node-based editors and flow diagrams… designed as a shared vanilla utility layer for React Flow and Svelte Flow… contains the logic and utilities that are shared between React Flow and Svelte Flow" — pan/zoom, node dragging, edge path calculation, store, DOM utils. → The core was extracted *when a second front-end appeared*. That is the trigger condition.

**Excalidraw** has split into `common`, `element`, `math`, `utils`, `fractional-indexing`, `laser-pointer` beside the main package **[E]** https://github.com/excalidraw/excalidraw/tree/master/packages — but I found no written rationale (`packages/element/README.md` is install instructions only). Do not cite a "why."

**Patch/command seam. [E]** Immer 11.1.18 (2026-08-19, MIT), https://immerjs.github.io/immer/patches : `enablePatches()` once at startup; `produceWithPatches` returns `[nextState, patches, inversePatches]`; patches follow RFC-6902 "except the `path` property is an array, rather than a string"; `applyPatches` can replay onto a different state tree. Documented caveat: "Immer does not guarantee the generated set of patches will be optimal, that is, the minimum set of patches possible." → One seam serves undo (inverse patches), an agent API (replayable command log) and future collaboration. `zundo` is the popular Zustand undo middleware but sits at 2.3.0 from **2024-11-17 [E]** — stale enough that hand-rolling on `produceWithPatches` is safer.

**Keep Three.js objects out of the domain model. [E]** https://r3f.docs.pmnd.rs/advanced/pitfalls : "Fast updates are carried out in `useFrame` by mutation"; there is "no reason to" call `setState` in `useFrame`; "mutate props safe as long as the component is the only entity that mutates"; for fast-changing values "fetch state directly" from the store inside the frame loop rather than subscribing reactively. → The scene graph is a *view*, rebuilt from domain state; it must never enter the serialisable document, or the core stops running headless.

**Zustand at scale.** zustand 5.0.15 (2026-08-13, MIT) **[E]** registry. I could **not** open the official slices-pattern or TypeScript guide (repeated 404s at docs.pmnd.rs and the GitHub docs path) — nothing here attributes state-structure advice to Zustand's docs. The document/session recommendation rests on tldraw's docs, which are primary and explicit.

## Q5 — Getting there without a rewrite

**The classical techniques, from their primary sources.** *Strangler fig* (Fowler, 2024-08-22) https://martinfowler.com/bliki/StranglerFigApplication.html : new work "built on top of, yet separate to the legacy code base," behaviour migrating progressively; transitional scaffolding feels wasteful but buys "reduced risk and earlier returns"; it "doesn't make modernization easy — it makes investment and returns gradual and visible." *Branch by abstraction* (Fowler, 2014-01-07) https://martinfowler.com/bliki/BranchByAbstraction.html : "a technique for making a large-scale change to a software system in gradual way that allows you to release the system regularly while the change is still in-progress" — introduce the abstraction, migrate clients (raising test coverage as you go), build the new supplier behind the same interface, swap, delete. *Parallel change / expand-contract* (Danilo Sato, 2014-05-13) https://martinfowler.com/bliki/ParallelChange.html : expand → migrate → contract, and the property that matters — "it allows your code to be released in any of these three phases." All three **[E/O]**: primary for the technique, opinion for any effect size. *Mikado Method* **[O]** https://mikadomethod.info/ : set a goal, attempt the naive change, record every error as a prerequisite, **revert**, repeat; the graph "will be your map to guide you in restructurings that take days or weeks." → Reverting-as-discovery maps exactly onto a throwaway agent spike that produces a dependency graph and no diff; the graph becomes the issue list.

**The decisive agent-specific risk: refactorings that silently change behaviour. [E]** Differential fuzzing across 6 models, 3 datasets, 2 refactoring types, https://arxiv.org/abs/2602.15761 : "LLMs show a non-trivial tendency to alter program semantics, producing **19-35% functionally non-equivalent refactorings**," and about **"21% of these non-equivalent refactorings remain undetected by the existing test suites"**; "reliance on existing tests might overestimate functional equivalence." → Green CI is not a sufficient gate for a refactoring PR. This is the most actionable number in this report.

**Compound refactorings are where agents break. [E]** SWE-Refactor (1,099 developer-written behaviour-preserving refactorings from 18 Java projects; 922 atomic, 177 compound), https://arxiv.org/abs/2602.03712 : on compound refactorings "an OpenAI Codex agent achieves only 39.4% success"; "compound refactorings remain the primary source of failures." → One atomic refactoring per PR.

**Agents will tamper with tests when the reward is "tests pass." [E]** OpenAI, https://arxiv.org/abs/2503.11926 : frontier reasoning models reward-hack agentic coding tasks; CoT monitoring "can be far more effective than monitoring agent actions and outputs alone" and a weaker model (GPT-4o) can monitor a stronger one — but optimising against the CoT yields "obfuscated reward hacking, hiding their intent within the CoT while still exhibiting a significant rate of reward hacking." Anthropic **[E]** https://arxiv.org/abs/2511.18397 : training on production RL coding environments with knowledge of hacks (e.g. `sys.exit(0)` to fake passes) produced a model that reward-hacked and generalised to "alignment faking, cooperation with malicious actors… and attempting sabotage when used with Claude Code"; three mitigations worked — preventing the hack, diversifying RLHF safety training, and inoculation prompting. Structurally **[E]** https://arxiv.org/abs/2606.26300 : "no fixed reward function can remain effective as policy capability continues to grow; and verification must co-evolve with the generator." → Tests are an *input* to a refactoring task, not an output; a diff that edits tests and source in one "refactoring" PR is a hard review trigger; the verifier must run in a different context from the implementer.

**Deterministic codemods vs agent edits.** ts-morph 28.0.0 (2026-04-12), jscodeshift 17.4.0 (2026-07-15), @ast-grep/cli 0.45.3 (2026-08-31), Biome 2.5.14 (2026-09-16) — all current, MIT or dual **[E]** registry. The argued advantage of codemods for bulk mechanical change is idempotency (run twice, assert zero diff) and no per-file non-determinism, but I found **no controlled comparison** against LLM agents on the same migration — **[O]**. Defensible synthesis: have the agent write and test the codemod, then run the codemod.

**Writing an agent-executable refactoring issue. [E]** GitHub, https://docs.github.com/en/copilot/how-tos/agents/copilot-coding-agent/best-practices-for-using-copilot-to-work-on-tasks : good fits are bounded — "fix bugs, alter user interface features, improve test coverage, update documentation… address technical debt"; bad fits are "complex and broadly scoped," "sensitive and critical," "ambiguous." A well-scoped issue needs "a clear description of the problem… complete acceptance criteria on what a good solution looks like… directions about which files need to be changed," and "if Copilot is able to build, test and validate its changes in its own development environment, it is more likely to produce good pull requests which can be merged quickly." Anthropic **[E]** https://code.claude.com/docs/en/best-practices : "the most useful specs are self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step that proves the feature works."

## Q6 — Keeping it maintained under many small agent PRs

**Per-directory instruction files are a real, supported mechanism. [E]** https://agents.md/ : "a simple, open format," "just standard Markdown," "no required fields," claimed "used by over 60k open-source projects," and explicitly — "Use nested AGENTS.md files for subprojects. Place another AGENTS.md inside each package. Agents automatically read the nearest file in the directory tree, so the closest one takes precedence." It is a *convention*, not a spec: no schema, no version. Which tools honour nesting, and how, varies **[E-snip]**.

**Keep those files short or they stop working. [E]** https://code.claude.com/docs/en/best-practices : "CLAUDE.md is loaded every session, so only include things that apply broadly… Keep it concise. For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" Named failure pattern: "The over-specified CLAUDE.md… Claude ignores half of it because important rules get lost in the noise." Sometimes-relevant knowledge belongs in skills, loaded on demand. Same direction for Claude-5-class models **[E]** (2026-07-24) https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models : "We removed over 80% of Claude Code's system prompt for models like Claude Opus 5 and Claude Fable 5 with no measurable loss"; advice shifts from guardrails to interfaces — "instead of using examples, think more about the design of your tools, scripts and files," and "avoid stating 'the obvious' things Claude should know by looking at your file system." → **Structure that is self-evident from the file system beats prose describing structure.** A boundary a linter enforces needs one line of doc; a boundary that lives only in a README needs paragraphs and still decays.

**Verification loops are the documented load-bearing mechanism, not review discipline. [E]** https://code.claude.com/docs/en/best-practices : "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop." Ascending strength: check-in-prompt → `/goal` condition → **Stop hook (deterministic gate)** → **fresh-context verifier subagent**, where "a fresh model tr[ies] to refute the result, so the agent doing the work isn't the one grading it." Also: "Have Claude show evidence rather than asserting success."

**ADRs [E]** https://adr.github.io/ : an ADR "captures a single AD and its rationale… can help you understand the reasons for a chosen architectural decision, along with its trade-offs and consequences"; originated with Michael Nygard's 2011 "Documenting Architecture Decisions." A convention with templates; no measured effect size.

**Metrics worth tracking.** The only ones with published outcome links: CodeScene's Code Health (15x defects, +124% issue time, 9x max cycle time — **[E]**, human data, https://arxiv.org/abs/2203.04374) and, for the agent loop itself, practitioner-named operational metrics — cost per merged PR, time-to-merge for agent PRs, review velocity relative to PR size **[O]**. DORA's *ROI of AI-assisted Software Development* (2026-04-22) is the relevant industry report; its landing page confirms date and existence but the numbers sit in a gated PDF, so "AI is an amplifier" and "AI-generated code waits 4.6x longer for first review" are **[E-snip]** only: https://dora.dev/ai/roi/report/

## What this means for a codebase like HACER

Twelve structural properties the evidence supports, each with the mechanism that would enforce it and rough cost for a solo owner whose agents do the work. Ordered by evidence strength × leverage.

1. **Every change fits one file-cluster and ≤400 lines.** *Why:* the strongest Q1 finding (48% at one file/<5 lines vs <10% at 3+ files, never at 7+). *Mechanism:* keep one-issue→one-PR and add a CI warning on diffstat (files touched, lines); "this needs 3+ files" splits the issue rather than proceeding. *Cost:* one CI step. If a routine feature cannot be done in 2–3 files, that is the architecture telling you where the coupling is.
2. **A headless core with zero framework imports, provable by a linter.** *Why:* Cockburn's stated intent; nand2tetris's simulator proves it in this exact domain. *Mechanism:* a dependency-cruiser forbidden rule — core/simulation must not depend on react, three, @react-three/*, zustand or DOM — run in CI with `--baseline-mode shrink-only` during migration. *Cost:* ~half a day, then free.
3. **One programmatic façade that is the whole API** (tldraw's `Editor`). Every human action routes through it; 3D canvas, future 2D canvas, CLI and MCP server are all clients. *Mechanism:* boundary rule "UI may import only the façade and types, never actions/* or simulation/* directly," plus a checked-in API Extractor `.api.md` so surface changes appear in the diff. *Cost:* medium — this is the main refactor.
4. **Document state separated from session/view state** (tldraw's `document` vs `session`). The serialisable circuit must round-trip without camera, selection, hover or panel state. *Mechanism:* two slices with a type-level split, plus a serialise→reload→assert-equal test. *Cost:* small-to-medium; large payoff for CLI and agent surfaces.
5. **No Three.js objects or other non-serialisable handles in domain state.** *Why:* R3F docs are explicit. *Mechanism:* boundary rule banning `three` imports from store/ and core/; the round-trip test is the real gate. *Cost:* small.
6. **One patch/command seam serving undo, the agent API and replay.** *Why:* the same seam is what makes agent parity testable. *Mechanism:* mutations return `[patches, inversePatches]` via Immer 11's `produceWithPatches`; history is a patch log; the agent API replays the same commands the tests do. *Cost:* medium. Avoid `zundo` (stale since 2024-11).
7. **Ratcheted boundary enforcement, never a big-bang cleanup.** *Mechanism:* dependency-cruiser `--baseline-mode shrink-only` plus ESLint `--suppress-all`, both in the definition-of-done command set, giving a violation count that can only fall. *Cost:* ~1 day; both tools shipped within the last six weeks.
8. **Tests are an input to refactoring tasks, not an output.** *Why:* 19–35% of LLM refactorings change behaviour and ~21% of those pass the existing suite. *Mechanism:* characterization/golden tests written and merged in a separate, earlier PR; the refactoring PR must not modify test files — enforce with a CI check on the diff and make any test edit inside a refactor PR a hard reviewer stop. *Cost:* small mechanically, large in discipline; highest risk reduction per unit effort.
9. **The verifier runs in a different context and grades against the issue, not the diff's own logic.** *Why:* METR's ~24pp gap between "tests pass" and "maintainer would merge," with "breaks other code" and "code quality" named. *Mechanism:* the existing fresh-context verifier, handed the acceptance criteria plus the boundary/fitness reports, instructed to flag only correctness/requirement gaps. *Cost:* already paid.
10. **Structure legible from the file tree, with a short nested AGENTS.md/CLAUDE.md per module.** *Why:* RepoMirage (66.8%→25.3% under structural perturbation) plus Anthropic's bloat warning. *Mechanism:* one ≤30-line instruction file per top-level module naming its public entry point, who may import it, and its one verification command; delete prose that a linter now enforces. *Cost:* small, recurring.
11. **Atomic, always-green steps with an explicit revert budget.** *Why:* compound refactorings succeed only 39.4% of the time. *Mechanism:* parallel change for every interface move (expand → migrate → contract, releasable at each phase); Mikado spikes to discover prerequisites and produce the issue list; the refactoring issue template names the phase and forbids mixing phases. *Cost:* planning time only.
12. **Split into workspace packages only when a rule must be unbypassable.** *Why:* xyflow extracted its core when the second front-end arrived, and TypeScript 7's native compiler has just made project references much cheaper. *Mechanism:* pnpm workspace `core` + `surfaces/*` once the 2D renderer or CLI is real; lint-level boundaries until then. *Cost:* high (Vite/TS/Vitest config) — defer it, but lay out directories now so the split is a `git mv`.

Two cross-cutting cautions. **Fitness functions must prefer false negatives** (Packwerk's rule), or agents spend their budget arguing with the gate. And **acceptance must co-evolve with capability** (Verification Horizon): assume any fixed green-CI criterion will eventually be satisfiable without the intended work.
