## 4. ADR-0020's amendment corrected the spike, and the tightening corrected the amendment

#433's verifier re-derived all seven fixtures independently against the real `compileHDL`; the
amendment's correction of the spike holds. One of its four nits was not style, and it is the one
that matters to **#374**, the next issue to read §1.5: **the boundary write-back does not survive
composition.** Raw `P({a:1})` gives `{out:0}`; wrapped with the §1.5 write-back, `{out:1}`;
registered and instantiated as `CHIP Q { IN x; OUT y; PARTS: P(a=x, out=y); }`, **`{y:0}`** — because
`evaluateChipWithCtx` returns `compiled(inputs, ctx)` directly (`src/core/chips/evaluateChip.ts:53`).
§1.5 now says the write-back belongs inside the chip definition a spec registers (§9/#190's
`'circuit'` composite evaluator) and that a composed chip pays it again at its own boundary. Read
§1.5 alone before this change and you would put it in the caller.

Also settled honestly rather than tidily: of §1.5's three stated reasons, only the **diagnostics
cost** carries the decision — the id shift is mitigable by §1.9's append-last rule and the width gap
is neutralised by the ADR's own width-generic export rule. Both are now labelled soft. The
`Or4`/`Or8` rejection now rests on `project01.ts` registering exactly the sixteen Project-1 chips,
which makes them invented chips in the compatibility baseline.

## 5. The process lesson: the controls that worked were not reviewers

The class named in `sessions/2026-09-23.md` §7 and owned by **#394** — stating a measured fact from
prose instead of from the artefact — recurred three times in one twenty-minute stretch of the
**coordinator's own** work:

1. `gh-merge-on-green` called a mergeable PR a `REAL FAILURE` because it treated *any* red check as
   fatal. Only `ci`, `pr-hygiene` and `browser-qa` are required here; `deploy-preview` and CodeQL are
   not. The PR was blocked for an unrelated reason — 12 commits behind.
2. The fix for that shipped a **worse** bug. `gh` writes API error bodies to **stdout**, so an
   unprotected-branch 404 was read as a context name — and a required-set file holding only that junk
   is non-empty, so the script would have believed it knew the required set and treated **every** real
   failure as non-blocking. A fix against refusing good merges nearly became one that accepted bad ones.
3. An issue was one step from being filed claiming `deploy-preview` is broken on docs-only PRs. On
   check: #432's head had **zero** failing checks, and the failures were on #416's pre-rebase head
   against a stale base. Not filed.

**What caught them.** (2) was visible only because the tool **printed the premise it had concluded**;
(3) because the same check was run against a **second** PR. Neither needed a reviewer. Each needed
one more measurement before the claim.

The generalisable control is (2): make a tool state the premise it is acting on, out loud, where the
next reader sees it. It is cheaper than review and it fires every time. The same pattern caught the
verifiers' finds this session — #432's "stated in all four places" claim fell to opening the fourth
file, and #434's builder claim about the line budget held up only because the brief was read.
