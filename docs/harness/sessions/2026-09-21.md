# Session record — 2026-09-21: the foundation question, and a change of direction

This is the committed memory of the 2026-09-21 session. It lets the work resume from the repo alone.
What to do next lives in `docs/portfolio.md` and GitHub Issues, never here. This page records the
owner's rulings, what was built, the state at hand-over, and how to pick up.

## 1. The goal

The standing goal is unchanged (`sessions/2026-09-18.md` §1): agents move HACER forward with very
little owner oversight. The day began as an autonomous run over harness hardening and ended somewhere
larger. The owner asked whether the codebase can carry that process at all, ruled that the foundation
is fixed before more is built on it, and changed what the product is: **a circuit is declared, not
drawn, and the 2D and 3D surfaces are read-only views of it.**

## 2. The owner's rulings (verbatim, in order)

1. **The run:** "Autonomously execute next items until our claude weekly limit reaches 50%, and of
   course you don't touch the fable model." On Cursor: "ration our usage equally across all days".
   At most 3 agents at once on the laptop. Led to `docs/harness/usage-rationing.md` (#319).
2. **Foundation first:** "is the codebase today structured to support our rigorous more-or-less
   autonomous process? Is it too tangled? Is it too monolithic? … we should prioritize all
   refactorings needed to put it in an optimal place before we add more features or fixes … we
   shouldn't build more on a wrong foundation that would crumble soon, so we have to fix the
   foundation first, and have to keep maintaining the foundation." Process work may go hand in hand.
3. **Wiring is declared, not drawn:** "a human should instead be able to specify wiring requirements
   via simple English words or some other simpler interface, and then auto wiring should happen …
   prompt/config driven, and suitable for MCPs and agents to work with … a human is likely going to
   say wire me this and not going to do everything by hand."
4. **Surfaces catch up more easily:** "the refactor should also consider making the catching up of
   the other surfaces (hdl, mcp and 2d) to the 3d smoother".
5. **Rendered surfaces are read-only:** "edits would be done via config specifications or prompts
   only, and surface re-renders, and only navigation actions would be allowed … if manual 2d/3d edits
   are ever needed we can consider that in the future".
6. **Testing is reconsidered too:** "are the existing e2es optimal? Is there a better, more robust
   and faster testing approach?"
7. **Remove, don't freeze — and 3D matters:** "I don't agree with freezing, working around a frozen
   code is hell … anything that should be removed should be removed, refactor deletion prs can be any
   size they need to be … 3d render surface have huge value even if it doesn't allow editing, because
   of its visual appeal … the 3d rendering of complex components will be one of its differentiators".
   This overruled a draft of the plan that froze the legacy canvas and ranked 2D ahead of 3D.
8. **Rendering is never finished:** "continual research of ai suited 3d browser rendering should be
   an important work … we might not be using the best libraries for the job … all that needs
   continual monitoring and improvement."

Judgment calls made on the owner's behalf are in §6 with their cost if wrong.

## 4. State at hand-over

**The plan is `docs/research/2026-09-21-foundation-audit/REPORT.md`.** Its §6a maps every plan item to
an issue. In one paragraph: the engine is sound and nearly headless; the tangle is the hand-editing
machinery — a 32-field state, a 125-entry action facade, a 678-line wiring function, a router that
depends on the order wires were drawn. The owner's direction removes that machinery rather than
untangling it. The target is one pipeline — spec → engine → `layout` → `route` → `describeScene` →
renderers as plug-ins — with 3D and 2D as first-class read-only views, and one small command set
shared by the shell, the CLI and MCP. The working rule is **replace → switch → delete, per
capability**: no frozen code, and deletion PRs are as large as they need to be.

The testing audit (`evidence/TESTING.md`) is part of it. Of 16 real defects on record, the verifier
found 7, people 3, code reading 3, and every automated layer except one `@store` spec found none. Of
114 browser test cases, 41 test gestures that are being removed, 40 belong in Node, 28 in a
canvas-less shell, and 5 are genuinely about 3D.

## 7. What the session learned

Today's rows are in `docs/harness/ledger.md`. The ones worth remembering:

- **A passing suite is a weak witness, and so is an agreeing reviewer.** The verifier that runs code
  found what every other layer missed. The strongest oracle available is differential: HACER's engine
  against the reference simulator on the official vectors (#338).
- **Builders do not see CI.** #312 and #322 both failed only in `browser-qa`, which a builder cannot
  run locally. The verifier reads the PR's CI logs (#334).
- **Dead code hides in test helpers.** 43 of 96 helper exports in `e2e/` have no caller, and nothing
  detected it (#332).
- **Agents that fork helpers hold the machine's slots.** With a cap of 3, one researcher and two
  helpers starve the queue. Say "no helpers" in the brief when the cap matters.
- **Do not make a reviewer's suggestion the default over the owner's direction.** A draft froze the
  legacy canvas because a reviewer argued for it; the owner had said remove.
